# G2.12A status

## Validated facts

- `multi-user.target` headless operation works and reduces idle memory use.
- NVIDIA CDI auto/NVML discovery fails on the tested Orin stack.
- CSV discovery generates a valid CDI spec.
- CDI GPU injection works before reboot.
- Early boot CDI generation can capture a transient DRM `card0`.
- After DRM stabilization, regeneration produces the final DRM topology and Docker CDI injection succeeds.

## Patch decision

The patch therefore:
- forces CSV discovery;
- preserves the NVIDIA service;
- adds an `ExecStartPre` helper through a systemd drop-in;
- waits for the NVIDIA platform DRM card + render node and a stable `/dev/dri` set;
- does not use a fixed sleep;
- does not touch `nvpmodel.service`.

## Required gate

A post-patch reboot plus real GPU container test is still required before marking
persistent CDI remediation PASS.

## G2.12A.4F ordering evidence

Observed boot ordering on the reference node:

- simpledrm minor 0: ~4.33 s
- Tegra DRM minor 1: ~7.55 s
- `nvidia-cdi-refresh.path`: ~9.21 s
- `nvidia-cdi-refresh.service`: ~9.47 s
- NVIDIA DRM loading starts: ~10.33 s
- early CDI enumeration captures transient `card0`: ~10.40 s
- NVIDIA DRM becomes minor 2: ~10.69 s
- NVIDIA framebuffer finalizes: ~11.14 s

The stock CDI service has no dependency on the final DRM topology. The AETHERIS
drop-in therefore uses a deterministic readiness helper rather than a fixed
sleep. The helper waits for the NVIDIA platform DRM device
`platform-13800000.display` to expose both card and render nodes, calls
`udevadm settle`, and requires the `/dev/dri` node set to remain stable across
multiple polls before allowing the stock `nvidia-ctk cdi generate` ExecStart.

This is intentionally a narrow workaround for the validated Jetson stack and
must be revalidated after NVIDIA/L4T/Container Toolkit upgrades.
