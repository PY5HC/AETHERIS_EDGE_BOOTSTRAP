# G3.3 — Governed Node Agent Release Model

## Authority and current source facts

This is a repository-only release contract. It does not build, install, copy,
activate, or remove anything under `/opt`, and it does not install a service.

The validated source authority is `PY5HC/AETHERIS_NODE_AGENT` at merged commit
`4bb897e6b18644199ac89ad33be9292e7487c37b` on `main`. The project uses
Hatchling, publishes the Python distribution `aetheris-node-agent` version
`0.1.0`, targets Python 3.11 or newer, and packages `src/aetheris_node_agent`.
Its web dependencies (`fastapi` and `uvicorn`) remain optional for library
installs, while the merged runtime lock covers the web deployment extra and
NumPy. No release manifest or production systemd definition exists at that
revision.

The source exposes `create_runtime_app()` and requires `AETHERIS_NODE_ID`.
It provides `/api/v1/health`, `/api/v1/node`, and `/api/v1/capabilities` routes.
That application factory is not itself an approved service executable. A
future Node Agent change must establish a real runner, signal behavior, bind
configuration, and readiness semantics before `ExecStart` is resolved.

## Immutable release layout

The proposed release artifact is a root-owned, immutable directory:

```text
/opt/aetheris/releases/<release-id>/
  manifest.json
  source/
  venv/
  bin/
  metadata/
```

The manifest is the release identity authority. `release_id` is unique and
immutable; it records the source repository and commit, UTC build time,
target architecture, Python version, package/version, artifact hash, and
dependency provenance. The artifact hash covers the exact release artifact
used by the activation gate. No in-place release mutation is allowed.

Governance provenance is recorded separately as repository
`PY5HC/AETHERIS_GOVERNANCE`, revision
`ff1318cd8f0a9720f66029e3985d1e5854044128`, and governance version `1.3.0`.
The applicable identity contract is `1.0.0`; no edge-node runtime profile is
published, so `profile` must remain `NOT_YET_ESTABLISHED`.

G3.0/G3.1 preserve `/opt/aetheris/current` as a directory. A future governed
migration may make it a symlink to a validated release, but:

```text
CURRENT_V1=DIRECTORY
FUTURE_MODEL=SYMLINK
MIGRATION_REQUIRED=YES
```

That migration is a separate gate and is not implemented here. No release is
activated merely because a directory exists.

## Manifest and provenance requirements

`schemas/node-agent-release-manifest.schema.json` defines schema version
`1.0`, the fixed source repository identity, an absolute governed release
root, a non-empty release ID, a 64-hex SHA-256, UTC build timestamp, Python
and architecture facts, package/version, dependency provenance, and a
relative executable path. The executable path must remain under the release's
`bin/` directory; it cannot point to PATH, a home directory, `/usr/local/bin`,
a container, or a development checkout.

The manifest must also identify health/readiness endpoints and activation
prerequisites. Release rejection criteria include malformed JSON, unknown
fields, unresolved placeholders, wrong repository, invalid commit/hash,
unsupported architecture, missing provenance, non-UTC timestamp, unsafe
paths, absent readiness information, or an artifact that cannot be verified.

## Build and activation model

An offline-capable future builder must use a recorded wheel/source artifact,
fully declared dependency provenance, a pinned Python interpreter policy, and
an aarch64-compatible environment. The Node Agent `requirements.lock` at the
source revision is hash-pinned for the web runtime and NumPy; the builder must
copy and verify that exact lock input and record its SHA-256 in release
metadata. The current lock SHA-256 is
`ce7d86147a73c9b701f57a0d7e11f968c9df9eae5c0430a3064171df64033b01`.

Activation requires: manifest validation; source commit and artifact hash
verification; architecture/Python compatibility; executable and dependency
checks; health/readiness probe success; root-owned release metadata; and an
atomic, separately reviewed promotion decision. No failed readiness check may
change `current` or silently select another release. Rollback requires a
previous validated release, a recorded activation decision, and an explicit
operator-governed selection; it is never an implicit fallback.

## Boundaries

Bootstrap owns validation and governed host authority. Release management
owns building and promotion. The future systemd unit reads the active release
and writes only its systemd-managed runtime/state leaves. It remains
`aetheris-node:aetheris`, with no sudo, Docker, GPU, or supplementary-group
authority. Docker/CDI and native GPU access are separate future capability
gates.

The current contract intentionally does not establish `ExecStart`: the source
repository lacks a production runner. A Node Agent repository change is
required before service materialization.

The concrete cross-repository proposal is:

```text
NODE_AGENT_EXECUTION_CONTRACT_CHANGE_REQUIRED=YES
proposed files:
  pyproject.toml
  src/aetheris_node_agent/runner.py
  tests/unit/test_runner.py
  tests/integration/test_runner_lifecycle.py
```

The Node Agent change should add a project-owned console script whose `main()`
constructs the application factory, reads an explicit governed configuration,
and runs the approved ASGI server. It must define bind host/port authority,
SIGTERM/SIGINT shutdown, startup failure behavior, and a readiness result.
The current source does not establish those values, so this proposal does not
guess them. The runner belongs in Node Agent because it owns application
lifecycle and HTTP serving; Bootstrap should only validate release provenance
and materialize a separately approved unit.
