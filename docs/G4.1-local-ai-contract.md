# G4.1 — AETHERIS Local AI Contract

G4.1 defines a backend-neutral contract for future local inference supporting
AETHERIS Knowledge and RF workloads. It does not install runtimes, acquire
models, bind ports, create services, or authorize Docker/GPU access.

## Authority and workloads

The dependency direction is AETHERIS Local AI Contract, then Governed Runtime
Adapter, then Validated Runtime Backend, then Governed Model Artifact.
Backend names are not capability declarations and remain replaceable.

Priority is Knowledge, then RF: retrieval augmentation, scientific/document
reasoning, citation-aware reasoning, embeddings, reranking, GraphRAG
assistance, document analysis, OCR/document preprocessing, RF event
interpretation, classification assistance, anomaly interpretation,
feature/result explanation, and environmental/context correlation.

Deterministic RF acquisition, DSP products, RAW IQ, feature vectors, source
documents, and canonical Knowledge provenance remain authoritative. LLM output
is interpretive or derived evidence and preserves source-evidence linkage
where applicable. AETHERIS SKY is deferred and has no G4 resource or runtime
authority.

## Model and adapter contracts

Supported model roles are generation, embedding, reranking, classification,
and experimental. A model record declares one or more roles; callers use
declared capabilities rather than infer behavior from runtime names.

An adapter exposes capability discovery and only supported operations:
load, unload, health, readiness, metadata, metrics, generate, embed, and
rerank. Generation, embedding, and reranking may use different models or
runtimes. Unsupported operations fail explicitly; there is no silent fallback.

Model provenance requires model identity, upstream revision and URI, license,
artifact/model digests, format, quantization, parameter count, backend and
version, acquisition/validation timestamps, hardware class, and validation
status. Missing provenance is rejected for validated scientific use.

## Resource and failure policy

LOCAL_AI_SMALL, LOCAL_AI_MEDIUM, and LOCAL_AI_EXPERIMENTAL are non-normative
until benchmark evidence exists. Admission evidence must measure resident
memory maximum, load peak, context, concurrency, CPU/GPU use, latency, and
role. Local AI yields to RF realtime DSP, RF feature extraction, RF ML
inference, Node Agent/platform stability, and Knowledge availability. No
numeric limits are canonical in G4.1.

Unknown digests, missing provenance, unsupported capability, unavailable
backend, load failure, out-of-memory, crash, health/readiness failure, and
resource-budget violation fail closed. They must not weaken G3 authority,
Node Agent health, RF acquisition, scientific RAW, or Knowledge provenance.

Runtime lifecycle is separate from model and service lifecycle. Proposed
runtime states are DISCOVERED, STAGED, VALIDATED, AVAILABLE, ACTIVE, DEGRADED,
FAILED, and RETIRED.

## Candidate runtimes

llama.cpp is the strongest initial experiment candidate because quantized GGUF
artifacts, aarch64/CUDA build provenance, and foreground execution can be
governed explicitly. G4.2 must capture source revision, compiler/toolchain,
CUDA/Jetson options, artifact hashes, runtime version, clean-room inputs, and
removal boundary.

Ollama remains a candidate. A later evaluation must establish aarch64/Jetson
GPU compatibility, binary provenance, model-store semantics, API behavior,
service isolation, resource controls, and reproducibility. Native TensorRT is
relevant for validated optimized models but is not a general backend contract.
PyTorch/Transformers are absent and optional, not G4 prerequisites.

## Benchmark evidence and scope

Benchmark records must capture node/model/runtime provenance, hardware and
power profile, input/context characteristics, load time, time to first token,
prompt/generated tokens, tokens/sec, RAM baseline/peak, CPU/GPU utilization,
temperature/power observations, result, and failure reason.

G4.1 creates schemas, a model template, and a read-only verifier only. No
runtime, model registry, model artifact, service, port, or live configuration
is created. G3 authority remains unchanged.
